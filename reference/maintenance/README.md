# 게스트 체험 종료와 DB 정비

2026-10-23 요청으로 게스트 발급·로그인·세션·비로그인 초안 작성·게스트 공개 설문과 회원 관리의 게스트 분류를 제거했다. 대체 화면은 `/#/M01002` 기능·템플릿 안내이며 `/api/showcase/templates`의 큐레이션 예시만 읽는다. 미리보기 입력은 저장·제출되지 않는다.

## 실제 DB 상태와 대기 조건

2026-10-23 읽기 전용 집계에서 게스트 작업공간 26개, 게스트 계정 26개, 게스트 설문 39개, 게스트 응답 8건과 일반 회원 작업공간 4개를 확인했다. 계정·접속정보·응답 원문은 출력하지 않았다. 현재 연결 계정에는 `DBA_CONSTRAINTS` 조회 권한이 없어 다른 스키마의 외래키 검증이 중단되었다. **실제 삭제·익명화·이용 중지 등 DB 변경은 실행하지 않았다.**

사용자는 종료·익명화 대신 **DBA 외래키 확인 후 물리 삭제**를 선택했다. DBA 확인 전에는 정비 도구의 `--apply`를 실행하지 않는다.

## DBA 확인 및 실행 절차

1. DBA가 [읽기 전용 점검 SQL](check-guest-retirement.sql)에 `SVY_OWNER` 바인드를 지정하고 실행한다. 결과 건수와 확인 시각만 공유하며 실제 스키마·계정·자격증명은 소스나 캡처에 남기지 않는다.
2. 외부 참조 또는 검토되지 않은 자식 테이블이 있으면 영향 범위부터 확인한다. 정비 도구가 공용 템플릿의 게스트 참조와 회원·게스트 혼합 소유권도 차단한다.
3. 변경된 애플리케이션의 게스트 차단을 적용한 뒤, DBA 확인이 가능한 기존 Oracle 연결 환경에서 `venv\Scripts\python.exe -B scripts/retire-guests.py`로 읽기 전용 사전 점검을 수행한다. 기본 명령은 데이터와 DDL을 변경하지 않는다. 실행 계정은 `DBA_CONSTRAINTS`를 조회할 수 있어야 하며 검증을 우회하는 옵션은 제공하지 않는다.
4. DBA 점검과 사전 점검이 성공한 경우에만 같은 명령에 `--apply`를 붙여 실행한다. 도구는 자신의 파일 위치를 기준으로 프로젝트를 찾으므로 작업 폴더와 무관하다. 프로젝트 venv Python 경로도 호출 위치에 맞게 절대 경로를 사용할 수 있다.
5. 정비는 `DB_GUEST` 전용 tenant의 세션·응답·보고서·발송 준비 데이터·설문·계정·tenant만 단일 트랜잭션으로 제거한다. 외래키나 제약을 해제하지 않고, 일반 회원 행 수 변화·게스트 잔존·건수 불일치·잠금 충돌은 전부 롤백한다. 작업 중 대상 테이블을 짧게 잠그며 `NOWAIT`로 활성 작업과 충돌하면 중단한다.
6. 적용 결과의 게스트 잔존 0건과 일반 회원 데이터 건수 유지를 확인한다. 이 변경은 DDL/ALT를 실행하지 않는다. 과거 설치와 업그레이드의 호환성을 위한 게스트 컬럼·테이블·함수·시퀀스는 이번 작업에서 파괴하지 않으며, runtime에서 발급·권한 부여에 사용하지 않는다.

## 검증

- `tests/test_frontend_guest_mode.py`: 발급 API 제거, 기존 게스트 접근 거부, 예시 API 비저장, 비로그인 업무 차단.
- `venv\Scripts\python.exe -B -X utf8 tests/browser_showcase.py`: 합성 데이터로 360/768/1440px 안내·검색·실패 재시도·격리 iframe·입력 비저장·키보드·회원 접근 경계를 확인한다. 실제 DB에 접속하지 않는다.
- Oracle 정비 도구의 성공적인 테스트는 실제 DB 삭제 성공을 의미하지 않는다. DBA 확인과 실제 적용 결과를 별도로 보고한다.
